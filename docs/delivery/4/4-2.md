# [4-2] Fix Velocity Loop Sign and Deadband Issues

## Description
Fix critical issues in the cascaded velocity control loop: incorrect PID sign causing positive feedback, deadband logic thrashing PID modes, and missing input clamping.

## Requirements
1. **Fix Velocity PID Sign**: Change from DIRECT to REVERSE mode to correct control direction
2. **Fix Deadband Mode Thrashing**: Stop toggling MANUAL/AUTOMATIC every 50ms - use state flag
3. **Add Input Clamping**: Clamp velocityInput to prevent garbage values from saturating loop
4. **Fix Debug Print Sign**: Correct velocity error calculation (setpoint - input, not input - setpoint)
5. **Add Sign Verification Print**: Clear debug output to verify correct behavior after fix
6. **Fix Reboot/Power-Cycle IMU Recovery**: After `wasReset()`, restore the same full-rate BNO085 startup behavior seen after flash upload

## Implementation Plan
1. Change velocity PID initialization from `DIRECT` to `REVERSE`
2. Add `static bool deadbandActive = false;` state flag
3. Replace deadband block with state-based logic:
   - Enter deadband once: Set MANUAL mode, zero output
   - Exit deadband once: Set AUTOMATIC mode, re-initialize
4. Add `velocityInput = constrain(velocityInput, -2.0, 2.0);` before Compute()
5. Fix debug print: `float velocityError = velocitySetpoint - filteredVelocity;`
6. Add sign verification print at 1Hz showing setpoint, filteredVelocity, angleFromVel
7. On every `wasReset()` (including the expected post-startup reset), call `enableIMUReports()` again after delays so SH2_RESET does not leave the hub with no rotation-vector subscription; do not call `begin_I2C()` from `loop()`

**How deadband thrashing is fixed:** Thrashing happened when the code toggled MANUAL/AUTOMATIC every 20 ms based on whether we were inside or outside the velocity deadband, which reset the PID integral and caused unstable behavior. The fix is to **transition only once** in each direction: when we first enter deadband (setpoint ≈ 0 and |velocity| < 0.08 m/s), set `deadbandActive = true`, call `SetMode(MANUAL)`, and zero the angle-from-velocity output; while in deadband do not call the PID. When we leave (setpoint non-zero or velocity outside deadband), set `deadbandActive = false` and `SetMode(AUTOMATIC)` once, then run the velocity PID as normal. See `teensy_balance_cascaded/TUNING_RECOMMENDATIONS.md` section "Deadband thrashing (fixed)" and firmware around the 20 Hz velocity PID block.

## Plan Change Log (Velocity Estimation Plan vs Implementation)

### Applied from plan
1. Added IMU velocity estimator path (Option A): pitch-rate integration with decay and clamping.
2. Routed outer-loop `velocityInput` from IMU estimate (replacing VESC-derived filtered velocity for control).
3. Added runtime `VEL_SCALE` tuning commands (`n`/`N`) for live scale calibration.
4. Kept VESC reads in background for diagnostics and comparison.

### Deviations from original plan and rationale
1. **Gyro rate reduced from 400Hz to 100Hz** (`GYRO_REPORT_INTERVAL_US = 10000`):
   - Rationale: reduced I2C bus pressure and improved startup robustness observed in-field.
2. **`dt` sanity window widened from `<0.01` to `<0.03` seconds** in estimator:
   - Rationale: at 100Hz, nominal sample period is ~0.01s and can jitter above 10ms; strict `<0.01` would drop valid updates.
3. **VESC signal kept visible in debug prints while control uses IMU velocity**:
   - Rationale: enables side-by-side validation and rollback confidence without reintroducing VESC noise into the control path.
4. **Motor command dispatch remains outside ISR** (prior structural change retained):
   - Rationale: avoids UART write contention and streaming stalls discovered during previous ISR-based write attempts.
5. **`wasReset()` recovery re-applies report configuration (double enable with settle delays), not `begin_I2C()` in `loop()`**:
   - Rationale: after `SH2_RESET`, report subscriptions are cleared; the code must call `enableReport` again or no rotation vectors arrive (`imuReadCount` stays 0). A brief attempt to run `begin_I2C()` from `loop()` after a bad `wasReset()` handling caused I2C probe failures (`I2C address not found`). The fix is to keep the SHTP session open and only re-send sensor config, matching startup timing without an extra transport teardown in `loop()`.
